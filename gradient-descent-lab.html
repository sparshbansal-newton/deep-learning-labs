How many times do the weights actually change?

Batch, Stochastic and Mini-Batch Gradient Descent are the same algorithm with one dial turned: how many rows you look at before you touch the weights. This worksheet fuses the rule, the code that implements it, and one running six-row dataset carried through every section — so the maths and the variable values agree line for line.

You run model.fit(X, y, epochs=10) on 400 rows. Ten epochs, 4000 row-visits — but how many times did the weight matrix actually change? The answer is not one number. It is entirely set by one argument you have not looked at yet.

Rule

updates per epoch = ⌈ N / B ⌉ N = training rows  ·  B = batch size  ·  ⌈ ⌉ = round up (the leftover rows still get their own update)

Six rows disagree with each other. Batch GD makes them vote, averages the ballot, and steps once. How far does one democratic step actually move a weight — and is it further or shorter than you would guess?

Rule

θ ← θ − η · (1/m) ∑i=1m ∇θ Ji with m = N: the sum runs over the entire training set before θ changes. 1 epoch = 1 update.
Vanilla batch GD — one vectorized pass, one update
import numpy as np

weights       = np.array([0.5, -0.5])
bias          = 0.0
learning_rate = 0.1

for i in range(epochs):
    # the ENTIRE dataset in one dot product
    z     = np.dot(X_train, weights) + bias
    y_hat = 1 / (1 + np.exp(-z))

    # gradient of the GLOBAL (mean) loss
    d_weights = np.dot(X_train.T, (y_hat - y_train)) / len(y_train)
    d_bias    = np.sum(y_hat - y_train) / len(y_train)

    # parameter update happens precisely ONCE per epoch
    weights = weights - learning_rate * d_weights
    bias    = bias    - learning_rate * d_bias

Same six rows, same starting weights, same learning rate — but update after every single row. If the destination is the same, does the extra bookkeeping buy anything? Watch w₂ carefully: at one point in the epoch it turns around and walks back.

Rule

θ ← θ − η · ∇θ Ji   for each i = 1 … N No sum, no division by m — the gradient of one row is the whole update signal. 1 epoch = N updates.
SGD — the Python-level loop that replaces the dot product
rows = X_train.shape[0]        # 6 in our example, 320 in the notebook

for epoch in range(epochs):
    # shuffle each epoch so row order stops being a systematic bias
    shuffled_X, shuffled_y = shuffle_data(X_train, y_train)

    for i in range(rows):
        x_point = shuffled_X[i:i+1, :]     # keep it 2-D: shape (1, 2)
        y_point = shuffled_y[i:i+1]

        y_hat   = 1 / (1 + np.exp(-(np.dot(x_point, weights) + bias)))
        d_w     = x_point.T * (y_hat - y_point)   # NO averaging - m is 1

        # fires `rows` times per epoch, not once
        weights = weights - learning_rate * d_w
        bias    = bias    - learning_rate * (y_hat - y_point)

The noise, measured

The Δw₂ column changes sign times inside a single epoch — the weight is repeatedly walked back by the next row's opinion. That is the "drunken walk", visible in six rows. Batch GD cannot do this: it has exactly one Δ per epoch, so it has nothing to contradict.

The six SGD step-losses average , but Batch GD's reported loss is . They differ not because one model is better — at step 1 they were identical — but because SGD measured each loss at a different θ. An SGD loss curve is a photograph of six different models; a batch loss curve is six photographs of one.

Rule

Var[∇batch] = Var[∇row] / B Averaging B row-gradients divides their variance by B. Smoothness is bought with batch size — and it is the only thing batch size buys you here.

The takeaway that trips people up

SGD's noise is not a defect you tolerate for speed. It is the same property, read two ways: the thing that makes the loss curve ugly is the thing that lets it climb out of shallow traps that would hold Batch GD forever.

Set batch_size=150 on 400 rows and Keras prints 3/3, not 2/2. Where does the third batch come from, how big is it — and why is nobody's default batch size ever 100?

Rule

updates = ⌈ N/B ⌉   ·   last batch = N mod B  (or B, when it divides evenly) Keras never discards the leftover rows — it ships a smaller final batch. That short batch still produces a full weight update.
Mini-batch — vectorized like Batch GD, frequent like SGD
for epoch in range(epochs):
    for start in range(0, rows, batch_size):
        Xb = X_train[start : start+batch_size]     # the last slice is just SHORT -
        yb = y_train[start : start+batch_size]     # Python clips it, no error

        y_hat = 1 / (1 + np.exp(-(np.dot(Xb, weights) + bias)))
        d_w   = np.dot(Xb.T, (y_hat - yb)) / len(yb)   # len(yb), NOT batch_size
        weights = weights - learning_rate * d_w

That highlighted line is the whole trick, and the one place this goes wrong in hand-written loops: divide by len(yb), not by batch_size. On the remainder batch those two differ, and dividing by the wrong one silently shrinks the final update of every epoch.

Why powers of two?

Memory hardware is addressed in binary. A batch whose row count is a power of two aligns cleanly onto physical RAM blocks and cache lines, so the transfer engine moves it without straddling boundaries. 50 and 100 look tidier to a human and are worse for the machine:

Two runs, same network, same 400 rows, same 10 epochs — one finishes in 3.3 seconds, the other takes 16.5. The slow one is the one you want. Both facts come from the same time.time() calls in the notebook.

Rule

wall-clock ≈ epochs × ⌈N/B⌉ × tstep(B) tstep grows far more slowly than B — a 320-row step is nowhere near 320× the cost of a 1-row step. Per-epoch speed and per-epoch learning are two different quantities, and batch size trades one for the other.

Batch GD's whole advantage is that np.dot(X_train, weights) is one fast matrix operation. That line has a hardware precondition nobody states out loud — and on ten crore rows it is the line that kills the process.

Rule

RAM for the feature matrix = B × d × bytes-per-float Batch GD sets B = N, so its memory bill scales with the dataset. Mini-batch fixes B, so its bill is constant no matter how many rows arrive.
The line with the precondition
# Batch GD: the ENTIRE X_train must be resident to form this product
z = np.dot(X_train, weights)     # X_train.shape == (100_000_000, d)  -> MemoryError

# Mini-batch: only `Xb` is resident; the rest can stay on disk
Xb = X_train[start : start+64]
z  = np.dot(Xb, weights)         # Xb.shape == (64, d)  -> fits in cache

And this counts only the input matrix. Activations, gradients and optimizer state are each allocated at the same batch dimension, so the real figure is a multiple of the column above — which is why the crash arrives sooner than the arithmetic suggests.

The resolution

Mini-batching is not a compromise between Batch GD and SGD on a single axis. It keeps the vectorization that makes Batch GD fast per step, keeps the frequent updates that make SGD fast per epoch, and additionally decouples memory from dataset size — a property neither extreme has. That is why 32/64/128/256 is what you actually see in production code, and why batch_size is the argument you tune first.

1 Lab Introduction

Gradient Descent (GD) is the optimization algorithm neural networks use to minimize a loss function J(θ) by repeatedly moving the parameters (weights & biases) in the direction opposite to the gradient — i.e. “downhill” on the loss surface.

In this lab we train the same network three times on a small purchase-prediction dataset, changing only one thing — the batch_size — and watch how that single choice trades training time against how fast the loss falls. Every GD variant plugs into the same backpropagation skeleton; what changes is only how many points are used before an update is applied.

Learning Objectives

  1. Tell Batch, Mini-batch, and Stochastic GD apart by their number of weight updates per epoch.
  2. Write a small PyTorch training function (fit) whose update frequency is set by the batch_size you pass it.
  3. Compare regimes by reading the printed per-epoch loss and total time.
  4. Relate each line of the PyTorch loop to the update rule Wn = W0 − η ∂L/∂w.
  5. Distinguish the two meanings of “fast”: speed per epoch vs. speed to convergence.

2 Conceptual Overview

2.1 What is Gradient Descent?

Training repeatedly updates each weight by stepping against the gradient of the loss:

Wn = W0 − η ∂L∂w
where W0 is the current weight, Wn the updated weight, η the learning rate (lr in the code), and ∂L/∂w the gradient of the loss with respect to that weight. In the loop, loss.backward() computes ∂L/∂w and optimizer.step() applies this formula.
Show intuition — why the minus sign?

The gradient ∂L/∂w points in the direction in which the loss increases fastest. We want the loss to go down, so we move the parameters in the opposite direction — hence the minus sign. The learning rate η decides how large that downhill step is: it scales the gradient before it is subtracted from the current weight.

2.2 Where Updates Happen — The Backpropagation Template

Every GD variant plugs into the same backpropagation skeleton — what changes is only how many points are used before an update is applied.

Backpropagation template
for epoch in range(epochs):
    # Loop over points depends entirely on the chosen GD Variant
    for point in dataset:  # select 1 single row
        prediction = forward_propagate(point)
        loss = calculate_loss(point, prediction)
        gradients = backward_propagate(loss)
        update_weights_and_biases(gradients)
    average_loss = calculate_epoch_average()
Key Idea

1 Epoch = one full pass over the training data. How many weight updates happen per epoch is exactly what distinguishes Batch GD, SGD, and Mini-Batch GD.

2.3 The Variants at a Glance

The variants differ only in how many samples feed each update, which fixes the number of updates per epoch:

VariantBatch size BUpdates / epoch
Batch GDall N1
Mini-batch GDe.g. 32N/B
Stochastic GD1N

More updates per epoch → the loss falls faster per epoch, but more time is spent per epoch. That tension is the whole lab.

3 Types of Gradient Descent

Select a variant to see what data it uses, how the update is performed, and its key characteristics.

Batch Gradient Descent (Vanilla GD)

In Batch Gradient Descent, gradients are computed across the entire dataset simultaneously before a single weight or bias is changed. The update direction reflects the average signal from every data point in the training set.

Rule: 1 Epoch = 1 Weight Update
Metaphor

Batch GD is like a collective, democratic decision-making process — every single data point casts a “vote” and the model takes exactly one careful step downhill based on the combined opinion of the whole population.

Pseudocode

Batch GD — pseudocode
import numpy as np

epochs = 10
weights = np.random.randn(input_dim, output_dim)
bias = np.zeros((1, output_dim))
learning_rate = 0.01

for i in range(epochs):
    # Process the ENTIRE dataset simultaneously (e.g. 50 points)
    y_hat = np.dot(X_train, weights) + bias

    # Cumulative loss across ALL samples combined
    loss = calculate_cumulative_loss(y_train, y_hat)

    # Gradient of the GLOBAL loss
    d_weights = compute_global_gradient(X_train, y_train, y_hat)

    # Parameter update happens precisely ONCE per epoch
    weights = weights - (learning_rate * d_weights)
    print(f"Epoch {i+1} complete. One update applied.")

Properties

  • Fully vectorized — one matrix dot product per epoch.
  • Very fast per epoch on suitable hardware (efficient use of NumPy / GPU matrix math).
  • Smooth, stable convergence path — low variance, low noise.
  • Needs many epochs to converge since it updates only once per pass.
  • Requires the whole dataset to fit in memory for the matrix multiplication.
How this variant appears in the PyTorch code

Batch GD is obtained by passing the full row count as the batch size, so the inner loop of fit() executes exactly once per epoch:

Batch GD run
model = build_model()
start = time.time()
fit(model, epochs=10, batch_size=n_train)     # whole training set in one batch
print('Total time:', round(time.time() - start, 2), 's')

Stochastic Gradient Descent (SGD)

SGD decouples dataset size from the update cycle: the data is shuffled and the model updates its parameters after every single row, one at a time.

Rule: 1 Epoch = N Weight Updates (N = number of training rows)

Example: 50 training rows → 50 parameter updates per epoch.

Metaphor

The SGD trajectory is compared to the unsteady path of someone walking home after drinking too much — an intentionally vivid image for an unstable, staggering, chaotic “drunken walk” across the loss landscape, rather than a straight line to the goal.

Pseudocode

Stochastic GD — pseudocode
epochs = 10
rows = X_train.shape[0]   # e.g. 50 rows

for epoch in range(epochs):
    # Shuffle dataset at the start of the epoch to reduce systemic bias
    shuffled_X, shuffled_y = shuffle_data(X_train, y_train)

    for i in range(rows):
        # Extract a single random point
        x_point = shuffled_X[i:i+1, :]
        y_point = shuffled_y[i:i+1]

        # Single prediction, single loss, instant update
        y_hat_point = np.dot(x_point, weights) + bias
        loss_point = calculate_loss(y_point, y_hat_point)
        d_weights_point = compute_point_gradient(x_point, y_point, y_hat_point)

        # Update triggers 'rows' times per epoch (e.g. 50 times)
        weights = weights - (learning_rate * d_weights_point)

    print(f"Epoch {epoch+1} complete. Total updates this epoch: {rows}")

Properties

  • Not vectorized across the dataset — a Python-level loop over rows.
  • Each epoch is slower to run than Batch GD (many small updates instead of one big matrix op).
  • High variance / noisy path — the loss can bounce up and down between updates.
  • Needs far fewer epochs to reach a good solution because it updates so frequently.
  • Only ever needs one row in memory at a time — memory-light.
Think

Q. Which one is faster (for the same number of epochs)?
Q. Which one is faster to converge (for the same number of epochs)?

Section 9 answers both using the numbers the two runs actually printed.

How this variant appears in the PyTorch code

SGD is obtained with batch_size=1, so the inner loop of fit() runs once per training row:

Stochastic GD run
model = build_model()
start = time.time()
fit(model, epochs=10, batch_size=1)
print('Total time:', round(time.time() - start, 2), 's')

The shuffle demanded by the theory is done by perm = torch.randperm(n_train) at the start of each epoch.

Mini-Batch Gradient Descent — The Middle Ground

Mini-Batch GD splits the dataset into small batches (e.g. 32 or 64 rows). Gradients for each batch are computed via vectorization, and a parameter update follows immediately after each batch.

Rule: 1 Epoch = N / B Weight Updates
Metaphor

Described as the “Middle Ground” / “Best of Both Worlds” — it combines the hardware acceleration of vectorization with the fast learning path that comes from frequent updates.

Why powers of two? (32, 64, 128, 256…)

  • Computer memory hardware is built on binary registers.
  • Choosing batch sizes as powers of two lets data align optimally within physical RAM blocks, maximizing data-transfer speed and low-level hardware performance.

The remainder batch — an edge case

When the chosen batch size does not evenly divide the total number of rows, Keras automatically creates a smaller final batch with the leftover rows.

Worked example

400 total rows, batch_size = 150 → 3 batches per epoch: Batch 1 (150 samples), Batch 2 (150 samples), Batch 3 (remaining 100 samples).

How this variant appears in the PyTorch code

Mini-batch GD is not run in Part 1 — this lab demonstrates only the two extremes, where the contrast is sharpest, and asks you to place mini-batch yourself in the checkpoints. It does appear once, as the warm-up call:

Warm-up call
fit(build_model(), epochs=1, batch_size=32)   # warm-up only; ignore this output

The hand-written slicing in fit() reproduces the remainder-batch behaviour on its own: perm[i:i + batch_size] simply returns a shorter slice at the end when batch_size does not divide n_train exactly. In Part 2 you will see how PyTorch’s DataLoader automates the batching done by hand here.

4 Loss-Curve Geometry & the Golden Nuggets

4.1 The Optimization Path

Zoomed in on a set of contour rings around the minimum, the two algorithms trace very different paths to the target.

AspectBatch GD PathSGD Path
ShapeStraight, smooth line perpendicular to the contour ringsJagged zig-zag, like a lightning bolt
CauseDirection computed from the whole population — high certaintyDirection computed from one sample at a time — high individual noise
Overall trendDrives directly to the deepest pointBounces around walls, but generally trends toward the base

4.2 Escaping Local Minima

On a non-convex, rugged loss landscape with several shallow local valleys plus one deep global canyon, the two algorithms behave very differently when they hit a shallow trap.

PathBehaviour at a shallow local minimum
Batch GDGradient from the smooth aggregate trend goes to zero at the base of the shallow valley — the model freezes and gets permanently trapped in the suboptimal local minimum.
SGDAn outlying data sample can cause a sudden large jump in loss/gradient. This noise “jolts” the optimizer out of the shallow valley wall, so it keeps moving until it finds the deeper global minimum.
Takeaway

SGD’s noise is not purely a weakness — that same instability is what lets it escape shallow local minima that would trap a smoother algorithm like Batch GD.

4.3 The Double Definition of “Fast”

There are two very different meanings of “fast” in this context, and confusing them is a common mistake.

Meaning of “Fast”Batch GDSGD
Speed PER epochVery fast — one efficient vectorized matrix operationSlower — many small sequential updates
Speed TO convergence (total epochs needed)Slow — only 1 update per epoch, needs many epochsFast — hundreds of updates within a single pass, needs far fewer epochs

4.4 Vectorization vs. Memory: The 10-Crore-Row Wall

Vectorization with NumPy dot products is very fast because it avoids slow Python-level loops — but it comes with a hardware cost.

  • A full-batch matrix dot product requires loading the entire dataset into RAM at once.
  • If the training set is massive (e.g. 100 million / 10 crore rows), this immediately causes an Out-Of-Memory (OOM) crash.
Fix

Mini-batching solves this hardware limit by only ever loading a small chunk of the dataset into RAM at a time.

Select a concept on the left. The matching lines of the fit() function are highlighted on the right.

Concept / Theory
How it appears in PyTorch
fit()
def fit(model, epochs, batch_size, lr=0.1):
    optimizer = torch.optim.SGD(model.parameters(), lr=lr)
    criterion = nn.BCELoss()

    for epoch in range(epochs):
        perm = torch.randperm(n_train)                 # reshuffle the rows each epoch
        epoch_loss, n_batches = 0.0, 0
        for i in range(0, n_train, batch_size):        # step through in batch_size chunks
            idx = perm[i:i + batch_size]               # indices of this batch
            xb, yb = X_train_t[idx], y_train_t[idx]    # slice out one batch by hand

            optimizer.zero_grad()             # 1. clear old gradients
            loss = criterion(model(xb), yb)   # 2+3. forward pass + loss L
            loss.backward()                   # 4. backprop -> computes dL/dw
            optimizer.step()                  # 5. update: W_n = W_0 - lr * dL/dw

            epoch_loss += loss.item()         # accumulate to report the epoch average
            n_batches += 1

        print(f'Epoch {epoch + 1:2d}/{epochs} - loss: {epoch_loss / n_batches:.4f}')
Pitfall — optimizer.zero_grad() first

PyTorch accumulates gradients; without clearing them, each batch corrupts the next.

6.3 Split, then Scale

Pitfall — scale after splitting

Fit the StandardScaler on the training rows only, then just transform the validation rows; fitting on everything leaks validation info into training.

Train/validation split and standardisation
X = df[['Age', 'EstimatedSalary']].values
y = df['Purchased'].values

X_train, X_val, y_train, y_val = train_test_split(X, y, test_size=0.2, random_state=2)

scaler = StandardScaler()
X_train = scaler.fit_transform(X_train)   # fit on train
X_val   = scaler.transform(X_val)         # transform val only

What happens: 20 % of the rows are held out for validation; the scaler learns its mean and standard deviation from the training rows only and is then applied to both sets.

Connection to gradient descent: Age (tens) and EstimatedSalary (tens of thousands) live on wildly different scales. Standardising them puts both features on comparable footing before the same learning rate η is applied to every weight.

6.4 Tensors and the Row Count N

Pitfall — label shape for BCELoss

The loss compares outputs of shape [N, 1]. Leaving labels as a flat [N] vector makes PyTorch broadcast to [N, N] and compute nonsense — so reshape to a column with .reshape(-1, 1).

NumPy → torch tensors
X_train_t = torch.tensor(X_train, dtype=torch.float32)
y_train_t = torch.tensor(y_train, dtype=torch.float32).reshape(-1, 1)
X_val_t   = torch.tensor(X_val,   dtype=torch.float32)
y_val_t   = torch.tensor(y_val,   dtype=torch.float32).reshape(-1, 1)

n_train = X_train_t.shape[0]   # number of training rows
print('training rows:', n_train)
Recorded output
training rows: 320

What happens: the arrays become float32 tensors, labels are reshaped into a column, and n_train records the number of training rows: 320.

Connection to gradient descent: n_train is the N of the theory. It is the number of updates SGD performs per epoch, the batch size that turns fit() into Batch GD, and the numerator of N/B for mini-batch.

6.5 The Model

A small network: 2 → 10 → 10 → 1 with a sigmoid output. build_model() returns fresh weights so each of the three runs starts from the same point (a fair comparison).

Model definition
def build_model():
    return nn.Sequential(
        nn.Linear(2, 10), nn.ReLU(),
        nn.Linear(10, 10), nn.ReLU(),
        nn.Linear(10, 1), nn.Sigmoid()
    )

What happens: three nn.Linear layers stacked with ReLU activations and a final sigmoid squashing the output into (0, 1) for binary classification.

Connection to gradient descent: the weights and biases inside those nn.Linear layers are the parameters θ that gradient descent updates. Rebuilding the model before each run is what keeps the Batch-vs-SGD comparison honest: both regimes start from the same point on the loss surface.

6.6 The Training Function

Keras’ model.fit() hides the training loop. Here we write that loop ourselves in a small fit() — so you can see exactly what happens on every batch. The number of times the inner loop runs per epoch (= updates per epoch) is set purely by batch_size.

fit()
def fit(model, epochs, batch_size, lr=0.1):
    optimizer = torch.optim.SGD(model.parameters(), lr=lr)
    criterion = nn.BCELoss()

    for epoch in range(epochs):
        perm = torch.randperm(n_train)                 # reshuffle the rows each epoch
        epoch_loss, n_batches = 0.0, 0
        for i in range(0, n_train, batch_size):        # step through in batch_size chunks
            idx = perm[i:i + batch_size]               # indices of this batch
            xb, yb = X_train_t[idx], y_train_t[idx]    # slice out one batch by hand

            optimizer.zero_grad()             # 1. clear old gradients
            loss = criterion(model(xb), yb)   # 2+3. forward pass + loss L
            loss.backward()                   # 4. backprop -> computes dL/dw
            optimizer.step()                  # 5. update: W_n = W_0 - lr * dL/dw

            epoch_loss += loss.item()         # accumulate to report the epoch average
            n_batches += 1

        print(f'Epoch {epoch + 1:2d}/{epochs} - loss: {epoch_loss / n_batches:.4f}')

What happens: the outer loop is one epoch; the rows are reshuffled with torch.randperm; the inner loop walks the shuffled indices in batch_size chunks, and each chunk performs the five numbered steps: clear gradients, forward pass, loss, backward pass, update. The batch losses are averaged and printed once per epoch.

Connection to gradient descent: this single function is all three variants at once. Because the inner loop is range(0, n_train, batch_size), it executes n_train / batch_size times — exactly the “updates per epoch” column of the theory table. Passing n_train gives 1 update (Batch GD), passing 1 gives N updates (SGD), passing 32 gives N/32 (Mini-batch).

6.10 Runs 3 & 4 — the Same Comparison over 100 Epochs

Why did the Batch GD timer read 0.0 s?

Not because training was free. The timer prints round(time.time() - start, 2), which keeps only two decimals — so anything under 0.005 s displays as 0.0. Ten Batch GD updates really take about 4.5 milliseconds, which is below the printed precision. Raising the epoch count to 100 lifts the measurement above that floor and lets us read a real number.

Both regimes are re-run with a freshly built model, changing only epochs=10 to epochs=100. Everything else — network, learning rate, data — is identical.

Connection to gradient descent: the longer run sharpens both halves of the tradeoff.

  • Convergence. After a full 100 epochs Batch GD reaches 0.3188 — a loss Stochastic GD had already beaten after its second epoch (0.2719). “Needs many epochs to converge” is no longer a prediction; it is measured.
  • Cost. Both regimes push the same amount of data through the network (100 × 320 = 32,000 row-passes each), yet SGD takes roughly 240× longer. The extra time is not extra arithmetic — it is the price of doing that arithmetic in 32,000 tiny Python-level steps instead of 100 vectorized matrix operations. This is the “Speed PER epoch” row of the cheat-sheet, in seconds.
  • Noise does not disappear. Stochastic GD flattens out around 0.22–0.23 and keeps bouncing to the very end (0.2260 → 0.2325). Batch GD’s curve stays perfectly smooth throughout.
A note on timings

Loss values are fully reproducible — the fixed seeds make every number above identical on any machine. Wall-clock times are not: they depend on your CPU, so expect the same ratio rather than the same seconds.

9.3 Observations Tied Back to the Theory

Observation in the recorded outputTheory it confirms
Batch GD: 10 epochs → 10 updates; loss 0.6661 → 0.6269. “1 Epoch = 1 Weight Update”; needs many epochs to converge since it updates only once per pass (Section 2).
Batch GD wall-clock rounds to 0.0 s over 10 epochs, and reads 0.02 s over 100. Very fast per epoch — one vectorized matrix operation (Sections 2, 4.3). The 10-epoch figure is a display artefact: two-decimal rounding hides the true ≈4.5 ms (Section 6.10).
SGD: loss reaches 0.3740 after a single epoch. “1 Epoch = N Weight Updates”; needs far fewer epochs because it updates so frequently (Section 3).
SGD loss rises at epochs 6, 7 and 10 instead of falling monotonically. High variance / noisy path — the loss can bounce up and down between updates; the jagged zig-zag of Fig. 2 (Sections 3, 4.1).
SGD takes 0.59 s versus 0.0 s for the same 10 epochs. Not vectorized across the dataset — a Python-level loop over rows, so each epoch is slower (Sections 3, 4.3).
Over 100 epochs Batch GD reaches only 0.3188 — worse than the 0.2719 Stochastic GD had after two epochs. Needs many epochs to converge since it updates only once per pass (Section 2); SGD needs far fewer epochs (Section 3).
At 100 epochs both regimes process 32,000 row-passes, yet SGD takes 5.46 s against 0.02 s — about 240×. Vectorization, not arithmetic volume, sets the cost: fully vectorized vs. a Python-level loop over rows (Sections 2, 3, 4.4).
Changing only batch_size moved time and convergence in opposite directions. The double definition of “fast”: speed per epoch vs. speed to convergence (Section 4.3).
Takeaway

Changing only batch_size moved both time and convergence — in opposite directions. “Faster” means different things for seconds vs epochs. Mini-batch GD sits between these two extremes, capturing most of stochastic’s fast convergence at a fraction of the cost — which is why it’s the practical default. 11 Lab Takeaways

Theory learned

  • GD minimises J(θ) by stepping against the gradient: Wn = W0 − η ∂L/∂w.
  • All variants share one backpropagation template; only the updates per epoch differ: 1, N/B, and N.
  • Batch GD is smooth but slow to converge and RAM-hungry; SGD is noisy, memory-light, converges in few epochs and can escape shallow local minima.
  • Mini-batch is the middle ground; powers of two align with binary memory registers, and a remainder batch handles leftover rows.
  • “Fast” has two meanings: per epoch, and to convergence.

What you implemented

  • Loaded and standardised the purchase-prediction data — scaling after the split.

  • Wrote an explicit fit() loop whose update frequency is set purely by batch_size.
  • Ran the two extremes for the same 10 epochs and compared loss and wall-clock time.
